Pulse

Jour 01. Un dashboard qui montre le rythme cardiaque de mes projets : chaque projet a une ligne de vie, et plus il est actif, plus elle bat vite.

rythme

Les battements par minute viennent de l'activité du dépôt. Un projet abandonné finit en ligne plate.

étatconditionrythme
actifAu moins un commit dans les 7 derniers jours46 + 5 par commit, 150 au maximum
calmeDes commits dans les 30 jours, aucun cette semaine36
endormiDernier push il y a moins de 90 jours28
ligne plateRien depuis 90 jours, ou dépôt introuvableaucun battement

La ligne du haut est la moyenne des projets qui battent encore. Quand un projet est branché en temps réel, son rythme de fond descend à 55 % pour que les vraies requêtes ressortent : une requête fait un pic, une connexion un pic plus haut.

brancher un serveur

Pour que le dashboard lise un serveur Express, il faut trois choses : un compteur, une route /stats et un flux en direct. Pour ProNote, le code est dans server/utils/stats.js.

Ce code est une version simplifiée : la vraie ajoute une limite de débit sur ces deux routes.

Le flux en direct

Chaque message ressemble à { "type": "requete", "n": 3 }. Le type est requete ou connexion, et les événements d'un même instant sont regroupés sur 150 ms. Le flux n'envoie jamais de chemin d'URL, d'adresse IP ni d'identité.

  • Le dashboard ferme le flux quand l'onglet passe en arrière-plan, et le rouvre au retour.
  • Le serveur accepte 100 spectateurs en direct au maximum.
  • La page d'accueil du serveur, /stats et les préflights CORS ne comptent pas comme du trafic.

limites

Ce que Pulse ne fait pas encore, et ce qui pourrait venir ensuite.

  • L'API GitHub est limitée à 60 appels par heure sans clé. Les réponses restent 30 minutes en cache, et le dashboard se met en pause jusqu'à l'heure de reprise donnée par GitHub. Plusieurs personnes sur le même réseau partagent cette limite.
  • « Site en ligne » veut dire que le site répond, pas qu'il répond correctement : un navigateur ne peut pas lire le code HTTP d'un autre site. La lecture de /stats règle ça pour les projets qui ont un serveur.
  • Le compteur est en mémoire : il repart de zéro à chaque redémarrage du serveur, déploiement compris.
  • Seul ProNote est branché en temps réel, car c'est le seul projet qui a un serveur à moi. Les autres cartes battent selon leurs commits.

Pistes

  • Une GitHub Action programmée qui écrit un fichier status.json : plus de limite d'appels, et l'état des builds de chaque projet.
  • Un historique de disponibilité : pourcentage sur 30 jours et courbe de latence par carte.
  • Écrire le compteur en base de données pour le garder entre deux redémarrages.
